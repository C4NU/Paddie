## 문서 규칙

**모든 프로젝트는 저장소 안에 `docs/`를 둔다.** 문서는 코드와 같이 커밋한다.

```
docs/
├── product.md      제품 정의 (또는 README.md — 문서 색인)
├── plan/           current · backlog · roadmap · code-review · revenue
├── tech-docs/      마일스톤이 끝나도 남는 지식 (설계·제약·함정)
├── guide/          반복 실행하는 절차 (배포·검증)
├── version/        버전별 결과
└── appstore/       스토어 문안·스크린샷 (앱 프로젝트만)
```

### 독자로 나눈다

🔴 **`plan/`은 사람이 읽고 `tech-docs/`는 AI가 읽는다.** 이 둘을 섞지 않는다.

| | 독자 | 성격 |
|---|---|---|
| `plan/` | 사람 | 체크리스트. 짧게 유지한다. **끝난 항목은 지운다** |
| `tech-docs/` | AI | 장기 기억. 쌓인다. **지우지 않는다** |

작업하다 알게 된 함정·원인·되돌릴 수 없는 결정은 `plan/`이 아니라 `tech-docs/`에 남긴다.
`plan/`에 교훈을 적으면 체크리스트가 읽을 수 없게 부푼다.

### plan/ — 좁혀 들어가는 세 단계

🔴 **`plan/`의 활성 문서는 아래 다섯 종류만 둔다.**

```
roadmap  ──→  backlog  ──→  current
전체 계획      이번 버전       지금 하는 것
              미작업 전체      체크리스트
```

| 파일 | 담는 것 | 상한 |
|---|---|---|
| `roadmap.md` | **앞으로 할 것만.** 끝난 버전은 `archive/`로 내린다 | 200줄 |
| `backlog.md` | **이번 버전**에서 아직 작업하지 않은 전체 목록. roadmap에서 가져온다 | 300줄 |
| `current.md` | backlog에서 지금 착수한 것. 체크리스트 | **150줄** |
| `code-review.md` | 리뷰가 찾은 것의 **제목과 한두 줄 요약만** | 200줄 |
| `revenue.md` | 상품·가격·권한의 **지금 상태**. ASC와 RevenueCat에서 읽어 적는다 | 200줄 |

**`roadmap.md`는 미래만 담는다.** 버전이 출시되면 그 절을 `archive/roadmap-vX.Y.md`로
통째로 옮긴다. 계획 문서에 완료 기록이 쌓이면 다음에 무엇을 할지가 안 보인다.

**`code-review.md`는 목록이지 보고서가 아니다.** 각 항목은 제목 한 줄과 요약 한두 줄로
끝낸다. 재현 절차·원인 분석·고친 코드는 `tech-docs/review/`에 따로 두고 링크만 건다.

```markdown
## CR-61 책 열기 전환에서 그림자 농도가 어긋난다
카드 그림자가 전환 소스 안에 있어 닫힘·플립·dismiss에서 값이 달랐다.
→ [tech-docs/review/cr-61-zoom-transition.md](../tech-docs/review/cr-61-zoom-transition.md)
```

스토어 상품이 없는 프로젝트는 `revenue.md`와 아래 ASC·RevenueCat 절차를 적용하지 않는다.

**`revenue.md`는 기억이 아니라 조회 결과를 적는다.** 상품 ID·가격·상태를 손으로 적어두면
곧 실제와 어긋난다. 아래 명령의 출력을 그대로 옮기고 **조회한 날짜를 함께 적는다.**

```bash
asc iap list --app <APP_ID>                                  # 상품과 상태
asc iap pricing summary --app <APP_ID> --territory KOR       # 지역 가격
```

RevenueCat 쪽(entitlement · offering · package)은 MCP로 읽는다. 원화 가격은 달러 환산이
아니라 **ASC가 주는 값**이므로 계산하지 않는다.

이 파일이 답해야 하는 질문은 넷이다 — **무엇을 파는가 · 얼마인가 · 사면 무엇이 열리는가 ·
지금 어떤 상태인가.** 정책의 근거와 개정 이력은 `tech-docs/product/`에 둔다.

**항목은 정확히 한 곳에만 있다.** backlog에서 current로 가져오면 backlog에서 지운다.
current에서 완료되면 지운다 — `[x]`를 쌓아두지 않는다. 남길 가치가 있으면 `tech-docs/`로 올린다.

상한을 넘으면 그 자리에서 정리한다. 넘긴 채로 두지 않는다.

### current.md 형식

상단에 요약을 두고, 본문은 체크리스트로만 쓴다.

```markdown
# current — v1.2.0

> **상태** `PREPARE_FOR_SUBMISSION` · 빌드 20260904.3 · 브랜치 `version/v1.2.0`
> **막힌 것** 두 번째 열 때 크래시 — 원인 미상
> **다음** W4 밤 시험 재측정 → W6 스크린샷 → 심사 제출

## 현재 진행중
- [ ] W4 라이브 액티비티 — 밤 시험 재측정

## 진행 예정
### W0 아이콘 통일
- [ ] 남은 판단 둘 — `fill: automatic`

### W5 곁들여 치우는 부채
- [ ] ViewfinderView 분해 — 타입 검사 한계에 닿아 있다

### W6 출시
- [ ] 스크린샷 두 장 첨부 (실기기 필요)

## 진행 불가
- [ ] 두 번째 열 때 크래시 — 원인 미상. 재고 나서 고친다
```

**세 묶음만 쓴다 — 현재 진행중 · 진행 예정 · 진행 불가.** 그 밖의 절을 만들지 않는다.
`진행 예정` 안에서 작업 단위는 **번호 오름차순**으로 놓는다(W0 → W5 → W6).

- **현재 진행중** — 지금 손대고 있는 것. 두어 개를 넘기지 않는다
- **진행 예정** — 이번 버전에 남았고 착수하면 되는 것
- **진행 불가** — 하려는데 못 하고 있는 것. 원인을 모르거나 외부 조건이 필요하다

🔴 **작업을 한 번 끝낼 때마다 `current.md`를 갱신한다.** 체크박스를 채우거나, 새 항목을
추가하거나, 상단 요약을 고친다. 세션이 끝날 때 몰아서 쓰지 않는다 — 그러면 빠진다.

### 약어

🔴 **새 약어 체계를 만들지 않는다.** 지금 같은 `P`가 Paddie에서는 우선순위이고
Rollie에서는 작업 번호다. 문서를 가로질러 읽을 수 없게 된 원인이다.

**약어를 단독으로 쓰지 않는다. 항상 이름을 병기한다.**

```
❌  W4를 먼저 닫는다
✅  W4 라이브 액티비티를 먼저 닫는다
```

프로젝트를 가로질러 뜻이 같은 약어는 다음 셋뿐이다.

| 약어 | 뜻 |
|---|---|
| `P0`~`P3` | 우선순위. 0이 가장 급하다 |
| `CR-##` | 코드리뷰 항목 번호 |
| `vX.Y.Z` | 버전 |

그 밖의 알파벳+숫자(`W4` · `M1` · `S1` · `Q4` …)는 **그 프로젝트 안에서만** 쓴다.
쓴다면 `roadmap.md` 상단에 무엇의 약자인지 한 줄로 적는다. 적지 않을 거면 쓰지 않는다.

### tech-docs/ — 기억의 궁전

AI가 매번 같은 경로로 찾아가도록 **방 이름을 프로젝트 간에 통일한다.**

🔴 **대소문자가 성격을 가른다. 소문자는 공통, 대문자는 그 앱 전용이다.**
이 구분이 "다른 앱에서도 찾을 수 있는 지식인가"를 한눈에 보여준다.

```
tech-docs/
├── README.md      입구 — 방 목록과 각 방에 무엇이 있는지
├── build/         빌드·아카이브·서명·생성 스크립트
├── core/          아키텍처·렌더링 코어·성능
├── platform/      OS 분기·Catalyst·하드웨어·버전 대응
├── data/          저장·마이그레이션
├── store/         ASC·심사·과금·RevenueCat
├── ui/            레이아웃·애니메이션·제스처
├── product/       제품 방향과 결정 로그 · 정책의 근거
├── review/        코드리뷰 상세 기록 (목록은 plan/code-review.md)
└── <전용>/        대문자. 그 앱만의 도메인
```

**문서가 없는 방은 만들지 않는다.** 빈 방은 찾는 사람을 헷갈리게 한다.

전용 방 이름은 각 저장소의 AGENTS.md에서 정한다.

**문서 이름은 kebab-case로 통일한다.** `snake_case`나 `PascalCase`를 섞지 않는다.

한 문서는 한 주제만 담고, 형식을 고정한다.

```markdown
---
room: store
tags: [asc, dsym, crash-report]
verified: 2026-09-04
severity: high
---

# ASC는 dSYM을 되돌려주지 않는다

**증상** — `asc builds dsyms`가 모든 빌드에서 `No dSYM files available`.
**원인** — Bitcode 폐기 후 Apple은 내려줄 dSYM을 만들지 않는다.
**대응** — 출시·심사 버전의 dSYM은 로컬 `archives/dsyms/`에 zip으로 보관한다.
**재발 방지** — 아카이브를 지우기 전 dSYM을 먼저 빼낸다.

관련: [[build/archive-retention]]
```

`verified` 날짜는 그 지식을 마지막으로 확인한 날이다. 오래된 문서를 만나면 다시 검증한다.

새 문서가 필요하면 성격에 맞는 폴더로 보낸다. 시점 스냅샷(핸드오프·컨텍스트 덤프)은
`plan/archive/`로 내린다.

**같은 정보를 두 곳에 두지 않는다.** 목록을 두 곳에 두면 한쪽만 지워도 티가 안 난다.
필요하면 상대 경로로 참조한다.
